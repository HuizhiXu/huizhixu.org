最近RSI真的太火了，正好 Lilian Weng 发了一篇关于Harness 和 RSI 的文章，信息量极大。我反复读了几遍，决定把它拆解成三篇，从我的角度来理解这件事。


## 一、什么是 Harness？

在 Lilian Weng 的文章中，Harness 被定义为**围绕基础模型搭建的系统，负责编排执行流程，决定模型如何思考、规划、调用工具、管理上下文和评估结果**。

这听起来和 Agent 没什么区别。那 Harness 和 Agent 有什么区别？

 我们熟悉的 Agent 概念包括规划、记忆、工具和执行四个部分。

![LLM Agent 的组成：规划、记忆、工具与执行](/images/articles/20260717/agent-overview.png)
（图来自：https://lilianweng.github.io/posts/2023-06-23-agent/）


而 Harness 在 Agent 的基础上增加了三层东西：
 1. **循环工程（Loop Engineering）** ：没有达到目标便持续运行。
 2. **文件系统作为长期记忆**：将日志、代码、中间产物持久化到硬盘上。
3. **自我改善系统**：能从自己的执行反馈中学习并改进。 这就是现在特别火的自我进化——Recursive Self Improvement。

简单理解，**Harness 就是一段代码，它规定了AI如何规划任务、如何调用工具、如何管理上下文和记忆、以及遇到错误时如何重试。**

因为它是代码，所以它可以被阅读、被修改、被评估——所以才可以进行自我进化。我之前就是没想明白这一点，所以很好奇它如何自我进化。


### Harness 的三大设计模式

好的 Harness 工程，都建立在三个核心设计模式之上。

#### 模式一：工作流自动化（Workflow Automation）

Harness需要有一套**闭环机制**。这个循环会一直持续，直到目标达成。Agent 里面也有循环，但是我感觉更多的是在最开始的时候补充缺少的输入，获得更多的上下文，重心没有放到整个流程循环。

 **规划（Plan）→ 执行（Execute）→ 观察/测试（Observe/Test）→ 改进（Improve）→ 再次执行**

举个具体的例子：Andrej Karpathy 的 autoresearch 项目，就构建了一个这样的自动化工作流—— AI 可以自主提出研究想法、编写代码、运行实验、分析结果，形成一个完整的研究闭环。



#### 模式二：文件系统作为持久记忆（File System as Persistent Memory）


Agent 也有记忆，但是如果把所有信息都塞进 Prompt 里，结果只有一个：上下文坍缩。在长周期的智能体任务中，实验日志、代码差异、错误轨迹、历史执行记录等中间产物，往往会**远远超过模型的上下文窗口长度**。

Harness 需要有一套外置存储机制。把日志、代码、中间产物写到文件中，能够随时去查阅。这是让 AI 能够处理长周期任务的基础。

这样做有两个好处：

1. **突破上下文窗口限制**：文件系统的容量远大于模型的上下文窗口。
2. **支持中断恢复**：即使任务被中断，模型也能通过读取文件恢复状态，继续工作。

#### 模式三：子智能体与后台任务（Sub-agent and Backend Jobs）

当任务变得复杂时，单个 Agent 工作远远不够。

Harness 支持**生成多个子智能体并行执行任务**——同时探索多个假设、并行运行实验、或将独立子任务委派出去，避免污染主上下文。

主智能体需要一个轻量级的**进程管理器**：启动任务、检查日志、取消失败的任务、合并结果。

关键设计原则是：**让并行变得显式且可检查**。如果子智能体的输出只存在于临时的聊天上下文中，很快就会丢失；但如果它们被存储为文件、日志和状态记录，模型就可以在中断后恢复，并基于自己的执行历史进行推理。

## 二、Harness 的优化方向

下面要说的是Harness 进行优化的两个方向，优化上下文工程和优化工作流。

### Harness 的上下文优化


#### 传统上下文的两大问题

**问题一：简洁偏置（Brevity Bias）**

给AI的指令太简洁，会导致结果偏差。

举个例子：如果你让AI检查一份财务报表，给它简洁的指令：“请检查这份报表，找出不合规的地方”。AI不会按照一个真正的审计师那样去审计。例如：要重点对比“毛利率”和“行业均值”；要调用外部工商数据库比对关联方交易。 
指令越简洁，AI 越倾向于依赖训练数据中的“通用模式”，而忽略特定领域所需的启发式规则和工具使用细节。

**问题二：上下文坍缩（Context Collapse）**


对话太长，很多 Chatbot 的做法是前20轮的对话被压缩成一小段话。多轮对话之后，早期的对话内容被压缩、总结，细节丢失。

#### ACE：动态上下文

为了解决这两个问题，Agentic Context Engineering（ACE）提出了**动态上下文**的概念。

ACE建立了**三个角色的隔离机制**：

1. **生成器（Generator）** ：负责执行任务，记录哪些策略带来了成功或失败。
2. **反思器（Reflector）** ：批判性地分析执行轨迹，提取出具体、可操作的教训（保留丰富的细节，对抗简洁偏置）。
3. **策展器（Curator）** ：将反思出的经验转化为结构化的条目，通过确定性规则合并到主上下文中。

为了不重写上下文，ACE 采用**增量更新**：将上下文拆解为结构化、条目化的知识点集合。有新经验时，只进行局部的、原子化的增量编辑——追加新条目或更新计数器，绝不触碰整体文本。

为了让知识不要变得更加冗余，ACE还采用了**Grow-and-Refine 机制**：
- **Grow** 
    - 无过滤追加：策展器会将所有新生成的增量条目（Delta）直接按章节追加到手册中。即使新知识点与现有内容相似，也会先保留下来。
    - 元数据更新：对于现有的知识点，系统仅通过更新计数器（如增加被标记为 helpful 或 harmful 的次数）等方式进行就地修订，绝不修改内容本身，从而规避了重写带来的信息侵蚀。
- **Refine**
    - 当知识库积累到一定程度后，系统会进行整理，剔除劣质和冗余内容。
        - 语义去重：利用语义嵌入Semantic Embedding 计算知识点之间的相似度。当相似度超过设定阈值时，系统会保留更详细、有用性更高的条目，将重复内容合并。
        - 投票淘汰：根据生成器在执行任务时提供的反馈，系统会清理表现不佳的条目。例如，移除被标记为“（harmful）”次数达到阈值的条目，并优先保留被标记为“（helpful）”次数较多的条目。
 

#### MCE：设计出Skill 让AI自己管理上下文管理

ACE虽然能从执行轨迹中自动学习并更新上下文，但**更新规则和工作流依然需要人工设计**。

Meta Context Engineering（MCE）更进一步：它把“如何管理上下文”的机制和“上下文里有什么内容”分离开来。

MCE引入了**技能（Skill）** 的概念：

- **静态部分**：提示词、知识库、代码库
- **动态部分**：搜索、筛选、过滤、格式化等操作

然后通过**双层优化**来让AI自主进化出最优的技能：

- **内层循环**：在给定技能下，寻找最佳上下文
- **外层循环**：在验证集上，寻找能带来最佳表现的技能

MCE不再强制执行ACE那种结构化的上下文规则，而是让技能和上下文共同迭代进化。

### Harness 的工作流优化

#### 传统工作流的问题

目前大多数AI系统的工作流都是由人类专家手工设计的。

一个典型的例子是 **The AI Scientist**：它构建了一个完整的科研自动化流水线，涵盖了提出研究想法、编写代码、运行实验、分析结果、撰写论文直到执行同行评审的全过程。每一步流程都是人类事先定义好的。

工作流的设计空间极其庞大，不应仅仅依赖人工手写，而应将其视为一个搜索问题，让算法和 AI 自动寻找最优解。下面介绍两个有代表性的工作，分别展示了两种不同的搜索思路。

#### **ADAS（Automated Design of Agentic Systems）**

ADAS将“智能体设计”本身表述为一个优化问题：

1. **初始化**：建立一个包含简单智能体（如CoT和self-refine）的工作流档案库
    
2. **代码生成**：“元智能体”受档案库已有方案启发，用代码编写新的工作流——先生成高层描述，再实现为代码
    
3. **自我修正**：草稿程序经过元智能体的两轮自我修正，检查其新颖性
    
4. **评估与归档**：评估每个新方案，将成功的方案加入档案库
    
5. **迭代**：不断重复，直到达到最大迭代次数
    

#### **AFlow：基于MCTS的图搜索**

AFlow把问题拆得更细——它将智能体工作流表示为一张**图**：

- **节点**：代表调用大语言模型的具体动作
    
- **边**：通过代码实现节点之间的逻辑操作与依赖关系
    
然后基于**蒙特卡洛树搜索（MCTS）** 进行迭代优化：

1. **初始化**：使用模板在搜索树中初始化起始工作流
    
2. **选择**：采用“得分与均匀探索的软性混合策略”，选择节点以平衡探索与利用
    
3. **扩展**：让LLM根据当前评估表现，生成修改后的新工作流
    
4. **评估**：执行并评估新工作流的性能
    
5. **更新树**：如果表现有改进，将新工作流加回搜索树
    
6. **终止**：直到分数收敛或达到预算上限
    

#### 两个方向的共同主线

把“优化上下文”和“优化工作流”放在一起比较，可以发现：**无论是上下文还是工作流，优化的都是Harness的局部。**

| 维度        | 传统做法           | 优化后的做法               | 本质                   |
| --------- | -------------- | -------------------- | -------------------- |
| **上下文优化** | 人工写Prompt、人工总结 | ACE动态管理、MCE自主进化Skill | 在**上下文管理**这个局部维度上做优化 |
| **工作流优化** | 人工设计流程         | ADAS代码生成、AFlow图搜索    | 在**工作流设计**这个局部维度上做优化 |


它们很重要，但还没有触及Harness的核心结构——**Harness 程序本身的代码逻辑**。当AI不再只是优化上下文或工作流，而是开始直接修改 Harness 程序本身的代码时，RSI（自我进化）才真正开始。这也正是下一篇要讨论的内容。


**下一篇预告：无论是上下文优化还是工作流优化，都只是在 Harness 的某个局部进化。下一篇，我们将进入真正的RSI范畴——Harness 如何实现自我进化？**
